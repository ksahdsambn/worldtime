## 一、项目概述

### 1.1 产品定位

WorldTime 是一个集**世界时钟、时区转换器、会议排期器**三位于一体的在线生产力工具，主要服务于：

- 跨国远程团队（安排会议、对齐工作时间）
- 国际商务人士（跟踪全球市场开盘时间、商务电话）
- 跨时区旅行者（倒时差、规划行程）
- 与海外亲友联络的个人用户

### 1.2 核心价值

把"看时间 → 换算时差 → 约会议"的完整链路**可视化到一张时间表里**，让用户免去心算时差、来回切换标签页的麻烦。拖一拖时间游标，所有城市时间联动；扫一眼颜色，就知道哪个时段所有人都方便开会。

### 1.3 与参考产品的差异

| 维度 | 本项目策略 |
|------|------------|
| 网页版 | 免费、无需注册 |
| 移动 App | **不做**（明确排除）|
| 桌面小组件 | 提供，可嵌入博客与企业网站 |
| 定价 | **完全免费**，无任何付费墙 |

## 二、术语表

| 术语 | 含义 |
|------|------|
| UTC | 协调世界时，全球时区计算的基准时间 |
| 时区 / IANA 时区 | 以"区域/城市"形式标识的全球时区标准，如"亚洲/上海""美洲/纽约" |
| 偏移量 | 某地时间相对于主地点（或 UTC）的小时差，如"加八""减五" |
| DST | 夏令时，部分国家在夏季将时钟拨快一小时 |
| 主地点（Home） | 用户指定的基准地点，所有偏移量以它为参照计算 |
| 昼夜状态 | 某地当前处于白天、夜晚、工作时间或睡眠时段的状态 |
| 工作时段 | 默认指某地本地时间九点到十八点，用户可在设置中调整 |
| 可联系时段 | 默认指本地时间六点至九点、十八点至二十二点，即早晚可联系但非标准工作时间 |
| 休息时段 | 默认指本地时间二十二点至次日六点 |
| 热力图 | 用红、橙、绿三色标注各时区工作时段重叠情况的时间表叠加层 |
| 选区 | 用户在时间表上拖选出来的一段连续时间，代表一个候选会议时段 |
| 游标 | 时间表上可拖动的竖向指示线，游标所在时刻所有时区实时联动显示 |
| 标签页 | 地点分组的一种切换方式，可按项目或团队把地点归类，通过顶部标签在不同分组间切换 |

## 三、用户故事与典型场景

### 3.1 跨国团队约周会

> 作为一位带领中美英三地团队的负责人，我希望添加三个城市的时区，一眼看出哪几个小时是三地都在工作时间的"绿色窗口"，然后把选中的时段一键导出到日历邀请同事。

### 3.2 跟踪海外市场开盘

> 作为一位金融从业者，我希望常驻查看纽约、伦敦、东京的开盘与收盘时段，避免在非交易时间误判行情。

> 备注：MVP 版本暂不提供"市场时段"专门预设，用户可通过添加城市并自定义工作时段近似实现；市场开盘/收盘时段预设为未来增强方向。

### 3.3 联系海外客户

> 作为一位销售，我希望知道现在给德国客户打电话是否合适，通过昼夜指示器判断对方是否还在工作时间。

### 3.4 规划跨时区旅行

> 作为一位即将出国的人，我希望对比出发地与目的地的时差，提前了解落地时的当地时间，便于安排接机与首日行程。

### 3.5 安排国际 webinar

> 作为一位活动组织者，我希望选定一个全球观众都相对合适的时段，生成一个公开链接，让报名者各自看到自己所在时区的对应时间。

### 4.3 会议排期器

**目标**：用色块高亮各时区的工作时段重叠情况，帮助用户一眼找到"所有人都合适"的会议时间。

#### 4.3.1 时段配色规则

配色基于每个地点的**本地时段类型**（工作时段、可联系时段、休息时段）逐格判定，再汇总到该列得到最终颜色。三类本地时段统一定义如下，**均可由用户在设置中调整**：

| 本地时段 | 默认范围（可配置）|
|----------|--------------------|
| 工作时段 | 本地时间九点至十八点 |
| 可联系时段 | 本地时间六点至九点、十八点至二十二点（即早晚可联系但非标准工作时间）|
| 休息时段 | 本地时间二十二点至次日六点 |

针对某一时段列（横轴上的某一小时）：

1. 逐一判定每个地点在该列所属的本地时段类型；
2. 取所有地点中的**最差状态**作为该列颜色，优先级从高到低为：休息时段 > 可联系时段 > 工作时段；
3. 任一地点为休息时段 → 该列**红色**；
4. 无休息时段但至少一地为可联系时段 → 该列**橙色**；
5. 所有地点均为工作时段 → 该列**绿色**。

| 颜色 | 含义 |
|------|------|
| 绿色 | 所有人都在工作时段 |
| 橙色 | 无人处于休息时段，但至少一人在可联系时段 |
| 红色 | 至少一人在休息时段 |

#### 4.3.2 周末与节假日覆盖规则（重要）

本规则把"休息日"（含周末与公共假日）视作强制的休息状态，优先于时段配色，确保不会在对方休息日误约会议。按版本分两阶段启用：

- **周末覆盖（P0，MVP 即生效）**：当某地点处于其所在地区的**周末**时，无论本地时间是几点，该地点在该列一律视为休息状态，参与"取最差状态"判定（即只要有一地处于周末，该列即为红色）。
- **节假日覆盖（P1，V1.1 启用）**：当某地点处于其所在国家的**公共假日**时，同样视为休息状态并参与判定。此能力依赖节假日数据（见 MS-7），在 V1.1 落地前，节假日不影响热力图。

> 注 1：周末规则按地点所在国家或地区的实际休息日判定，不依赖固定举例，随各地实际作息自动适配。
> 注 2：节假日标记（MS-7）为 P1，MVP 阶段不具备节假日数据，故 MVP 验收仅覆盖周末覆盖。

## 六、特色功能

### 6.1 Google 日历叠加

在时区网格上叠加用户 Google 日历的**空闲与忙碌时段**，帮助快速找出真正空档。需在设置中通过一次性授权连接 Google 账号。此项为**可选增强**，不授权也能使用全部核心功能；该授权仅用于读取空闲/忙碌信息，不构成账户体系，用户可随时断开。优先级 P2。

### 6.2 周末智能识别

系统根据各地点所在国家或地区的实际休息日自动判定周末列并高亮，自动适配非周六周日的周末情形（如部分地区周五周六休或周日单休）。优先级 P0（已含于 TC-11 与 4.3.2）。

### 6.3 DST 夏令时预警

在某地点夏令时切换前一周，系统自动弹出或标记提醒；在网格对应日期边界显示"夏令时切换"提示。优先级 P1。

### 6.4 时区详情悬浮

鼠标悬停在"与主地点的偏移量"上时，显示详细时区信息，包括 UTC 偏移、当前是否夏令时、下次切换日期。优先级 P1。

### 6.5 地点高级管理

在 WC-6 已提供的基础管理（拖拽排序、删除、设置主地点）之上，进一步增强：

- **重命名**：自定义地点显示名
- **标签分组**：按项目或团队给地点分组，通过标签页切换

优先级 P1。

### 6.6 可分享链接

将当前所有地点与选区状态编码进链接，生成可分享地址。他人打开链接即复现同样视图，无需登录。优先级 P0（已含于 MS-6）。

### 6.7 日出日落信息

除了单纯的昼夜二分，进一步显示各地实际的日出与日落时刻，帮助用户更精确判断对方的光照与作息情况。优先级 P2。

### 6.8 明暗主题切换

提供浅色与深色两套主题，用户可手动切换或跟随系统设置，长时间使用更护眼。优先级 P1。

### 6.9 打印与导出图片

把当前时间表打印或导出为图片，便于附在邮件中或打印张贴。优先级 P2。

### 6.10 键盘快捷键

常用操作支持键盘完成，例如方向键移动游标、删除键移除地点、组合键确认选区。优先级 P2。

## 七、桌面小组件

供用户嵌入到博客、企业官网、内部知识库的轻量展示组件。**整体优先级 P2**，列入 V1.2 版本规划。

### 6.1 世界时钟小组件

展示若干指定城市的实时时间，以可嵌入组件形式提供。可配置城市列表、主题色、十二或二十四小时制。

### 6.2 事件小组件

展示某个事件在多个时区的对应时间。嵌入后访客可看到"该活动在我所在时区是几点"。可配置事件时间、城市列表、展示语言。

## 九、页面布局说明

整体采用**上下分栏 + 左右分栏**的结构：

- **顶部导航栏**：放置品牌标识、城市搜索框、设置入口（含小时格式、工作时段、主题切换）以及分享按钮。
- **左侧地点列表面板**：纵向排列用户已添加的地点，每个地点显示国旗、城市名、当前时间、昼夜状态、与主地点的偏移量；列表顶部固定显示 UTC 基准时间行；底部提供"添加地点"入口。
- **主时间网格区域**：占据页面主体，横轴为日期，纵轴对应左侧地点；格子按小时排列，叠加红橙绿热力图色块；支持拖拽选区与可拖动时间游标；周末与节假日列有明显标识。
- **底部操作栏**：选中时段后出现，提供导出到各日历应用、复制时间摘要、生成邮件链接、生成公开事件页与复制分享链接等操作。

移动端将地点列表与时间网格上下堆叠，时间网格横向滚动，操作栏固定在底部不溢出。

## 十二、验收标准

> 标注对应版本：V（MVP，对应 P0）或 E（增强，对应 P1）。MVP 验收以 V 项为准。

1. 【V】**添加城市**：输入"东京"，下拉出现带日本国旗的"东京（JST，UTC 加九）"，点击后出现在列表。
2. 【V】**时区联动**：拖动时间游标到"北京十四点"，纽约一栏同步显示"凌晨两点"，并标注为东部夏令时。
3. 【V】**同日凌晨**：北京十四点对应纽约**当天**凌晨两点（北京领先十二小时，时刻更早，不跨日）；网格上纽约行该列应清楚呈现为当天凌晨时段，并在视觉上与白天区分。
4. 【V】**夏令时**：伦敦在三月末网格边界出现"由 GMT 切换到 BST"的提示。
5. 【V】**跨日橙色**：北京九点对应纽约**前一天**二十一点；二十一点属可联系时段，无人处于休息时段，故该列应为**橙色**而非红色，并在视觉上与前一日区分。
6. 【V】**热力图优先级**：以纽约与伦敦为例，纽约二十二点（休息时段）时伦敦为次日三点（同样属休息时段），该列存在休息时段故应为红色，验证"取最差状态"规则。
7. 【V】**全绿场景**：构造所有地点均在本地九点至十八点的同一列，该列应为绿色。
8. 【V】**周末覆盖**：添加一个所在地区周末为周五、周六的地点后，周五、周六两列自动高亮为周末，且这两列在热力图中整列显示为红色。
9. 【E】**节假日覆盖**：在美方公共假日当天，纽约行整列标红，影响全局热力图判定（节假日标记属增强项，MVP 不强制）。
10. 【V】**导出日历**：选中时段后点击导出，下载的日历文件可被 Outlook 正常导入并显示正确的各地时间。
11. 【V】**复制时间摘要**：选中时段后点击复制，粘贴得到包含各地点本地时间的文本摘要。
12. 【V】**分享链接**：复制链接到另一浏览器打开，地点列表与选区状态完全一致，且全程无登录弹窗。
13. 【V】**UTC 基准行**：地点列表顶部固定显示一条 UTC 时间，不随主地点切换而改变；其他地点偏移量仍以主地点为基准。
14. 【V】**小时格式切换**：在设置中切换十二/二十四/混合三种格式，所有地点的时间显示立即随之改变；混合模式下各地点保留本地原生格式。
15. 【V】**选区时长**：拖选一小时三十分钟后，操作栏明确显示"时长：一小时三十分钟"。
16. 【V】**回到现在**：把游标拖到三天后再点击"回到现在"，游标立即回到当前时刻。
17. 【V】**响应式**：在手机宽度下，地点列表与网格上下堆叠，网格可横向滚动，操作栏不溢出屏幕。
18. 【V】**数据持久**：刷新页面后，地点列表与设置保持不变。
19. 【V】**无注册**：全程不出现任何登录或注册弹窗。
20. 【E】**城市对着陆页**：访问某城市对路径，页面展示两地固定时差与当前时间对照表，且服务端返回的原始 HTML 即包含完整内容（爬虫无需执行脚本）。
21. 【E】**时区缩写着陆页**：访问某时区缩写对路径，页面解释两时区缩写含义与偏移，并给出转换示例，原始 HTML 即包含内容。
22. 【E】**着陆页可索引**：上述着陆页均含页面元数据与结构化数据，可被搜索引擎收录（属增强项，V1.1 上线）。

## 十四、技术架构

> 本章为技术决策记录，便于研发对齐与后续维护，不改变前文的产品需求。

### 14.1 总体定位

- **形态**：服务端渲染的单页应用。核心交互（时间网格、拖拽选区、热力图）在浏览器端完成，页面外壳与 SEO 内容在服务端预先生成。
- **后端**：不设自建业务后端，所有时区计算与用户数据在浏览器端完成；服务端仅承担页面预渲染与按需生成，供搜索引擎抓取。
- **部署形态**：以容器化方式交付，运行一个 Node 进程提供页面服务。

### 14.2 技术选型

| 层 | 选型 | 选型理由 |
|----|------|----------|
| 框架 | Next.js（App Router）+ React + TypeScript | 大规模按需静态生成（ISR）成熟度最高；React 生态最成熟；TypeScript 为复杂时间逻辑提供类型安全 |
| 运行模式 | Node 服务器模式（非静态导出）| 启用 ISR，支持大规模城市对按需生成并缓存，扛住海量长尾组合 |
| 时区计算 | Luxon（基于浏览器 Intl）| 自动处理 IANA 时区与 DST，是 JavaScript 生态最准确的时区方案 |
| 拖拽交互 | dnd-kit | 无障碍友好，支撑地点排序与选区边缘微调 |
| 状态管理 | Zustand | 轻量，便于做 URL 状态序列化（支撑分享链接）|
| 样式 | Tailwind CSS | 时间网格为高度自定义布局，原子化样式最灵活 |
| 国际化 | next-intl | 配合服务端渲染实现中英双语 |
| 节假日数据 | 静态数据文件，构建期打包 | 频率低，随版本更新即可 |

### 14.3 为什么是这个方案

在「成熟度 + 重度 SEO」的交集下逐一比较主流候选：

- **静态导出方案**出局：构建期需枚举全部城市对，组合数量为城市数的平方量级，构建不可行。
- **Gatsby 类纯静态生成框架**出局：同样依赖构建期枚举，海量页面构建耗时数小时，且无按需生成能力。
- **Astro**：纯 SEO 性能极强（默认零 JS、最快首屏），但在大规模动态路由 + 按需生成这条路上成熟度与实战案例不及 Next.js 的 ISR，放回"重度 + 大规模 + 成熟可靠"场景下更稳的选择仍是 Next.js。
- **Next.js（Node + ISR）**：大规模按需生成久经验证，是同类头部工具站的实际技术路线。

结论：在重度 SEO + React + 成熟可靠的交集下，Next.js Node 模式是当前最优解，无明显更优替代。

### 14.4 渲染与 SEO 策略

针对重度 SEO 打法，按页面类型采用不同渲染策略。对应的页面产品需求见第五章：

| 页面类型 | 渲染策略 | 上线版本 | 说明 |
|----------|----------|----------|------|
| 首页 | 构建期静态生成（SSG）| V1.0 | 完整 HTML 直出，爬虫秒收 |
| 热门城市对页（数百个高频组合）| 构建期静态生成（SSG）| V1.1 | 头部词索引最快、权重最高，如北京-纽约、伦敦-东京 |
| 长尾城市对页（上万组合）| 按需生成 + 缓存（ISR）| V1.1 | 首次访问才生成并缓存，扛住海量组合，无需构建期枚举 |
| 时区缩写页（如 EST 转 PST）| 构建期静态生成（SSG）| V1.1 | 高搜索量词，静态化收益高 |
| 公开事件页（MS-5）| 按需生成 + 缓存（ISR）| V1.1 | 每个事件页可被搜索引擎收录，带长尾流量 |
| 交互组件（网格、选区、热力图）| 客户端水合 | V1.0 | 交互体验无损 |

> 说明：MVP（V1.0）仅有首页（SSG）与交互组件（客户端水合）；所有 SEO 着陆页与事件页均随 V1.1 上线，与第五章、十一章优先级一致。

每个静态生成的着陆页均包含完整的服务端 HTML、页面元数据与结构化数据，确保爬虫无需执行脚本即可看到内容。

> 头部词与长尾词分层是关键：热门组合预生成保索引速度与权重，长尾组合按需生成保可扩展性，两者结合是同类站点的标准打法。

### 14.5 状态与数据

- **用户数据**：地点列表、设置、选区全部存于浏览器本地存储，刷新后保持不变，符合"无需注册、数据本地化"定位。
- **分享链接（MS-6）**：将地点与选区状态序列化进 URL，打开链接即还原视图。
- **节假日数据**：构建期打包为静态资源，随版本发布更新；V1.1 启用前不影响热力图。

### 14.6 交付与部署

- 以容器化方式交付，镜像基于 Node 运行时。
- 构建阶段执行生产构建，运行阶段启动 Node 页面服务。
- 需保证进程常驻与按需生成缓存的可持久化（缓存目录挂载为持久卷）。
